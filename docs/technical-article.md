# 背景を「装飾」から「状態」へ変える — slide-atmosphereの設計と検証

スライドの背景は、最後に写真を貼る場所になりやすい。写真が強すぎると本文が埋もれ、弱すぎると画面全体が無機質になる。slide-atmosphereでは、この問題を「背景画像をきれいにする」だけで解かず、季節・時間帯・天気・景色・スライド役割をひとつの状態として扱うことにした。

この設計を進めた結果、既存の宇宙・花火・湖・都会を含む26種類の景色を、表紙・章扉・本文・引用・締めの役割と組み合わせて編集できるようになった。追加した自然系の景色は、海中、田舎、快晴、深海、初日の出、木漏れ日、竹林、桜霞、紫陽花、花畑、紅葉、雪原、砂丘、月夜の海、オーロラ、山霞、潮だまり、雲海、藤棚、石庭、夕渓谷。この記事では、景色の数を増やすことよりも、増やしても画面が散らからない仕組みを説明する。

## 1. まず「何を選んでいるのか」を定義する

画面の状態は次の5項目で表す。

~~~text
WorldState = season + period + weather + scene + role
~~~

seasonは春・夏・秋・冬、periodは朝・昼・夕・夜、weatherは晴れ・曇り・雨・雪、sceneは景色、roleは表紙・章扉・本文・引用・締めである。

重要なのは、これらをDOMの見た目から逆算しないことだ。state.mjsのSTATE_OPTIONSを唯一の許可リストにして、URLから読み込む値も、編集操作から入る値も、必ずnormalizeStateを通す。不正な値が来たときは既定値へ戻るので、共有リンクや古い保存データが画面を壊さない。

URLにはこの状態をそのまま保存する。

~~~text
/?season=spring&period=night&weather=snow&scene=sand-dunes&role=content
~~~

同じURLは同じ初期状態を開く。景色を増やすときも既存のキーは変更せず、新しいキーを追加するだけにした。この「キーを壊さない」方針が、過去のリンクと保存済みスライドを維持する土台になっている。

## 2. 実装はカタログを中心に流す

景色ごとの条件をapp.jsやstyles.cssへ個別に散らすと、追加のたびに分岐が増える。そこでscenes.mjsにカタログを置き、UIと描画が同じデータを参照するようにした。

~~~mermaid
flowchart LR
  A[scenes.mjs<br/>scene catalog] --> B[state.mjs<br/>normalize URL state]
  B --> C[app.js<br/>render and interaction]
  C --> D[styles.css<br/>layers and typography]
  A --> E[assets/<br/>local WebP]
  C --> F[deck.mjs<br/>browser storage deck v1]
~~~

カタログの最小単位はkeyとlabelだが、自然系の景色には次の表示メタデータも持たせる。

~~~text
{
  key: "forest-light",
  label: "木漏れ日",
  family: "soft",
  art: "./assets/scene-forest-light-v1.webp",
  dayOpacity: 0.44,
  eveningExposure: 0.52,
  nightExposure: 0.45
}
~~~

familyは描画の系統、toneは暗い景色かどうか、artはローカル画像、dayOpacityと各periodのexposureは文字と写真のバランスを表す。画像そのものに明るさ調整を焼き込まず、状態に応じた値をデータとして残すことで、後から調整理由を追える。

app.jsは選択されたキーからdata-scene-family、data-scene-tone、CSSカスタムプロパティを設定する。スライド本体、デッキのサムネイル、景色選択ボタンが同じカタログを使うので、「本番だけ写真が違う」「選択中のプレビューだけ暗い」といったズレが起きにくい。

## 3. 画像生成では「主役」と「余白」を同時に指定する

各景色は16:9、1672×941の素材として生成した。共通プロンプトでは、次の条件を固定している。

- 写真らしい自然な奥行きと、画面の右側・下側に残る構図の情報量
- 左側約60%と中央付近を、タイトルを置ける静かな面にする
- UI用の背景なので、ロゴ・文字・人物・看板など読める人工物を入れない
- 画面全体を埋めるが、輪郭を細かくしすぎない
- その景色らしい色は残し、彩度を上げすぎない

この指定は「何を描くか」より「どこを空けるか」を優先している。背景の美しさは被写体の密度だけで決まらず、文字が置かれる面の静けさで決まるからだ。

生成後は元のPNGを反復調整用に残し、実行時はlossless WebPへ変換した。アセットの対応表とプロンプトは[scene-expansion-prompts.md](./scene-expansion-prompts.md)に、採用条件と検証結果は[landscape-presets.md](./landscape-presets.md)に記録している。

## 4. 「全部ぼかす」ではなく、景色の系統を分ける

自然系の21景色はsoft familyとして扱い、5〜11px程度のぼかし、少し抑えた彩度、レイヤー越しの明るさ調整を使う。これで花や霧、海面、砂の細部が本文へ競合しにくくなる。

一方、宇宙は同じ処理に入れない。星雲の輪郭と粒状感を残した方が世界観が出るため、spaceには独立した露出・不透明度・文字用シェードを設定している。深海、月夜の海、オーロラ、潮だまりは自然系だがtone=darkとして別扱いにした。暗い写真に通常の明るいグラデーションを重ねると、時間帯の意味が崩れるため、暗いベースと控えめな季節マークを使う。

styles.cssのレイヤーは、概念上次の順で重なる。

~~~text
base gradient
  -> seasonal light
  -> weather wash
  -> vignette / noise
  -> scene image
  -> role-aware content shade
  -> text
~~~

写真はscene-markの背景として置き、CSS変数landscape-art、landscape-opacity、landscape-exposureで制御する。画像に直接文字を合成しないので、同じ素材をサムネイルや書き出しにも再利用できる。表示時には必要に応じてblur、saturate、brightnessを組み合わせるが、spaceのように輪郭を残す系統には適用しない。

## 5. 可読性は感覚で終わらせず、状態を横断して測る

同じ景色でも、朝と夜、表紙と本文では必要なコントラストが違う。本文は情報量が多いので背景を落とし、引用は少し見せ、表紙は写真の印象を残す。自然系の昼は暗い文字、夕方と夜は明るい文字という切り替えを基本にし、景色固有の例外だけカタログ値とCSSの限定ルールで調整した。

最終確認では、1440×960のChromium上で、先行追加した10景色について4つの時間帯と5つの役割を組み合わせた200状態を生成した。各状態のタイトル・本文・補助テキストを文字単位の矩形でサンプリングし、最小コントラストを計算した。タイトルは3以上、それ以外は4.5以上を合格条件にした。

~~~text
測定対象: 200状態 × 3テキストフィールド = 600フィールド
失敗: 0
景色ごとの最小値:
木漏れ日 4.92 / 竹林 5.55 / 桜霞 5.63 / 紫陽花 4.69 /
花畑 5.99 / 紅葉 4.70 / 雪原 5.69 / 砂丘 4.89 /
月夜の海 8.71 / オーロラ 9.75
~~~

これは「どの写真でも文字が読める」という数学的な証明ではない。既定コピー、既定フォント、1440×960、4時間帯、5役割という条件での回帰ベンチマークである。ただし、調整した景色を同じ条件で横並びにできるので、目視だけで判断するより再現性が高い。

## 6. 選択肢が増えても、操作は増やさない

景色が5個のときのUIを、そのまま横に伸ばすだけでは26個を扱えない。scene-choicesは5列×6行にして、ラベルとスウォッチを同じリズムで並べた。390px幅でもラベルが切れないことを確認している。

キーボード操作では、左右移動を1つ、上下移動を現在のグリッド列数だけ進める。列数を5とハードコードせず、getComputedStyleで実際のgrid-template-columnsを読んでいるので、レスポンシブで列数が変わっても上下キーの意味が崩れない。HomeとEndも追加し、26個の候補をマウスだけで探さなくてよいようにした。

選択したsceneがnone以外ならweatherは景色側に吸収されるため、天気ボタンは無効化する。これは機能を隠すのではなく、「今どちらを編集しているか」を画面上で明確にするための制約である。

## 7. デッキ操作と共有URLを別の責務にする

スライド操作はdeck.mjsの純粋関数に閉じ込めた。duplicateSlideは元のstateとcontentを新しいIDで複製し、deleteSlideは最後の1枚を守りながら隣のスライドを選択する。moveSlideは配列の端でクランプする。UIはこの結果を保存し、サムネイルを再描画するだけなので、クリック・キーボード・ドラッグで同じ挙動になる。履歴も不変スナップショットとして別モジュールに切り出し、編集入力は入力中に増やさず、フォーカスを外した時点で1操作として記録する。Undo / Redoは直近50操作を保持し、新しい操作を記録した時点でRedo側を捨てる。

ランダムな空気感と現在時刻は、選択中の1枚だけを変えるとデッキの統一感が崩れるため、デッキ全体へ1操作として適用する。各スライドの役割・文章・順番は保持し、共有URLにデッキpayloadがある場合は変更後の全スライドを同じ履歴単位で更新する。景色ボタンの個別変更は、スライドごとに異なる背景を作れるように従来どおり残す。

キーボードは発表モードの矢印操作と衝突しないように分けた。編集画面ではCtrl/Cmd+Dが複製、Deleteが削除、Alt+ArrowUp/Downが前後移動になる。Ctrl/Cmd+ZとCtrl/Cmd+Shift+Zはプレビュー中にデッキ履歴を戻し、編集中はcontenteditable本来の文字編集を優先する。入力欄とcontenteditableではブラウザ本来の編集を優先する。

共有ボタンは現在のWorldStateに、正規化済みデッキをbase64urlで追加する。deck-share.mjsでエンコードと復元を行い、壊れたpayloadや48,000文字を超えるURLは受け付けない。受け取ったデッキはそのタブのsessionStorageに一時保存するので、手元の下書きを上書きせず、その後の編集を続けられる。景色のOG画像はカタログに対応する静的アセットへ切り替え、タイトル・説明・URLと同じタイミングで更新する。
## 8. 何を検証したか

今回の景色追加では、次の3種類を分けて確認した。

1. Nodeの単体テスト35件。stateの正規化、scene catalog、deckの保存・復元、content、コンパクトな操作ボタンのアクセシブルネームを確認した。
2. ChromiumのUI検証。26個の候補、5列グリッドのキーボード移動、シーン切り替え時のメタデータ初期化、天気の無効化、共有・再読込、編集、2枚以上のスライド、発表表示、6つの画面幅を確認した。
3. 既存シーンの回帰比較。カタログ連携の前後で、同じ位置・同じサイズ・トランジション無効の条件にそろえ、20シーンの描画がピクセル単位で変わっていないことを確認した。

検証スクリプトはアプリ本体と分離している。記事で示した数値を更新したいときは、dist/expansion-contrast.cjsを実行して画像を取り直し、dist/expansion-contrast.pyで再計算すればよい。

## 9. この設計から得たことと、次にできること

背景を装飾として扱うと、景色を増やすほど個別調整が増える。状態とカタログとして扱うと、増やすべきものは景色の定義、画像、必要なら数個の露出値に絞れる。美術的な判断は画像生成とプロンプトに残し、実装上の判断はstate・CSS変数・検証スクリプトに残す。この役割分担が、見た目の自由度と回帰のしやすさを両立させた。

今後は、選択した状態から1920×1080 PNGを自動生成する処理、天気APIとの連携、景色の並べ替え、背景の強度をUIから微調整する機能を追加できる。ただし、どれもWorldStateの境界とカタログの安定したキーを守ることが前提になる。

実装を追うときは、次の順に読むと全体像を掴みやすい。

- [scenes.mjs](../scenes.mjs)：景色カタログと表示メタデータ
- [state.mjs](../state.mjs)：URLと選択状態の正規化
- [app.js](../app.js)：状態反映、UI、キーボード操作
- [styles.css](../styles.css)：背景レイヤー、文字色、レスポンシブ
- [deck.mjs](../deck.mjs)：スライドの保存・復元・複製・削除・移動
- [history.mjs](../history.mjs)：Undo / Redoの不変スナップショット履歴
- [deck-share.mjs](../deck-share.mjs)：デッキ共有URLのエンコード・復元
- [scene-preferences.mjs](../scene-preferences.mjs)：景色のお気に入り・最近使った景色の保存
- [scene-expansion-prompts.md](./scene-expansion-prompts.md)：生成プロンプトとアセット対応
- [landscape-presets.md](./landscape-presets.md)：採用基準と検証結果
- [design-analysis.md](./design-analysis.md)：企画・リスク・実装判断

景色を増やした結果として大切だったのは、26個を並べたことではない。どの景色を選んでも、時間帯・役割・文字量に合わせて背景の強さが変わり、同じURLでその状態を再現できることだった。



## 10. 公開buildを再現可能にする

build/はソースの手動コピーにせず、scripts/build.mjsで生成する。CIではnpm run check:buildを実行し、ローカル検証と公開ファイルのずれを検出する。
