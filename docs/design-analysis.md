# プレゼンテーション背景の設計分析

## 結論

このプロジェクトの価値は、天気や昼夜が変わるアニメーションではありません。プレゼンテーションに「その場の空気」を与えながら、内容の可読性と発表の構造を守ることです。

したがって、背景は次の優先順位で設計します。

1. 可読性
2. 状態の再現性と本番の安全性
3. スライド間の階層
4. 個性と世界観
5. 動きや技術的な面白さ

## 企画上の強み

### 1. 既存の個人活動と接続できる

個人サイト、記事、ポートフォリオ、発表資料が別々のデザインになるのではなく、「静かな環境」「記録」「観測」という共通する視覚言語を持てます。

### 2. 季節・天気・時間帯・景色は装飾ではなく状態になる

春・夏・秋・冬、晴れ・雨、昼・夜を大きなイラストで説明するのではなく、色温度・明るさ・彩度・ノイズ量の変化として扱います。季節だけは低彩度のアクセントカラーをスライド下部に薄く置き、プレゼン中の情報を邪魔しないまま背景に意味を持たせます。花火・湖・都会・宇宙に加えて16種類の自然景色を景色軸として扱い、細部を読ませる写真や細かい粒子ではなく、ぼかした輪郭・低コントラストの光・静かな星空で表現します。

### 3. コード生成は再利用性が高い

画像を1枚作るのではなく、ルールから複数の背景を生成できます。表紙、区切り、本文、引用、締めを同じシステムから作ることで、資料全体の統一感を維持できます。

## 最大のリスク

### 動きが主役になる

雨粒や雲の動きを目立たせると、発表内容より背景に視線が行きます。MVPでは動きを入れず、状態が変わったときの色の遷移だけに留めるのが安全です。

### 本番環境に依存する

天気APIやネットワークに依存すると、会場で再現できない可能性があります。発表用には、URLパラメータで状態を固定するモードと、画像書き出しの経路が必須です。

### 1種類の背景では資料の階層が弱い

天気・時間帯だけで全ページを表現すると、表紙と本文が同じ重みになります。`role` を第三の状態軸として設け、光量・余白・ビネット・コントラストを制御します。

### 参考サイトの雰囲気に寄りすぎる

静かな編集的デザインを参考にするのはよい一方、特定サイトの模倣になると個人の発表資料としての理由が弱くなります。「背景は環境であり、装飾ではない」という原則を独自の軸にします。

## 状態モデル

```text
WorldState
  ├─ season: spring / summer / autumn / winter
  ├─ period: morning / day / evening / night
  ├─ weather: clear / cloudy / rain / snow / unavailable
  ├─ scene: 32種類の景色プリセット（scenes.mjsで管理）
  └─ role: cover / section / content / quote / closing
```

### season

季節は背景全体を塗り替える軸ではなく、夜の背景に薄い編集テーマを与える軸です。春は淡いピンク、夏は少し青、秋はもみじ色、冬は白〜青白を使います。色はスライド下部のぼかした光としてだけ残し、季節を説明する記号やイラストは置きません。

本文の中央領域には季節の装飾を置かず、下部のぼかした色だけで季節を伝えます。色面の境界線や水平な切り替えは作りません。

### period

明るさと色温度を変えます。朝は少し暖かく、昼はニュートラル、夕方は暖色と紫、夜は青みのある暗色にします。

### weather

背景の彩度、コントラスト、光の広がり、ノイズ量を変えます。天気の記号やイラストは使用しません。

天気による彩度・コントラストの調整は背景ステージにだけ適用し、タイトル・本文の文字色とコントラストには影響させません。

### scene

景色は独立した背景レイヤーです。noneでは現在の静かな背景をそのまま使い、宇宙は精細な星雲、自然景色は26種類の被写体を細部が読めない程度にぼかした横長画像で示します。景色を選んだときは雨・雪・曇りの大気処理を重ねず、専用レイヤーを文字の背後に置いて中央の安全領域を守ります。雪で粒がノイズになった反省から、景色も情報量を増やしすぎず、画像の色面だけを残します。

### role

情報の階層を表します。表紙は光量を少し上げ、本文は中央を静かにし、引用は余白を広く、締めは周辺を少し落とします。

### content

タイトル・本文・小見出しは環境状態とは別のコンテンツです。編集モードではプレビューを見ながら直接更新し、役割ごとにブラウザへ下書き保存します。背景の共有URLに文章を埋め込まないことで、URLの再現性と文章の編集性を分離します。

## デザインの安全領域

- 中央60〜70%は文字・図表用にする
- 強い光は左右の端や四隅に寄せる
- 季節の色は下部のぼかしとして置き、本文の安全領域に侵入させない
- 景色画像は文字の背後に置き、中央の可読性を優先する
- 天気のフィルターは背景ステージに限定し、文字のコントラストを保持する
- 景色は細部や粒子ではなく、ぼかした色面と光で示す
- 原色は避け、白・黒に少量の色相を混ぜる
- 背景の彩度より文字のコントラストを優先する
- 本文スライドでは背景のコントラストを表紙より下げる
- プロジェクターや会場照明で明るく見える前提で調整する

## 技術選定

### 採用

- HTML: プレビューの構造
- CSS: グラデーション、状態、レスポンシブ、モーション制御
- SVG: 控えめな粒状感
- JavaScript: DOMイベントと表示反映
- `state.mjs`: 状態の正規化、URL変換、デフォルト値
- Node.js標準テスト: 状態変換と静的サーバーの純粋な検証
- CSS グラデーション / 背景画像レイヤー: 湖面・都会・花火の低コントラスト表現

### 後回し

- Canvas: 大量の粒子や雨を実装する必要が出るまで不要
- WebGL: プレゼン背景には過剰で、再現性と保守性を下げやすい
- フルCMS: 背景生成のMVPの目的から外れる

JavaScriptは見た目を直接描画せず、「現在の状態を決める」役割に限定します。見た目はCSSで定義することで、色の調整と検証を容易にします。

## MVPの境界

### P0

- 16:9プレビュー
- 4つの季節
- 4つの時間帯
- 4つの天気
- 32種類の景色プリセット（なし・花火・湖・都会・宇宙・海中・田舎・快晴・深海・初日の出・木漏れ日・竹林・桜霞・桜並木・紫陽花・花畑・紅葉・雪原・砂丘・月夜の海・オーロラ・山霞・潮だまり・雲海・藤棚・石庭・夕渓谷・霧の港・雨の窓・白樺林・夜の灯台・Rust Forge）
- 5つのスライド役割
- 手動選択
- 編集モードでタイトル・本文・小見出しを変更
- URLで状態を固定
- オフライン動作

### P1

- 現在時刻モード
- 天気APIと正規化層
- API失敗時の固定フォールバック
- 1920×1080 PNG書き出し
- reduced motion

### P2

- PowerPoint / Google Slides向けの書き出し
- 発表用の静止画と、確認用のライブ表示の分離
- 自分のサイトや記事のOG画像との共通テーマ化

## 検証項目

- 1920×1080で中央の本文が読めるか
- 4季の色面が本文より先に目立たないか
- 花火・湖・都会の画像を選んでも文字が読みやすいか
- 明るい会場と暗い会場で文字が沈まないか
- 表紙・本文・区切りの重要度が視覚的に分かれるか
- 15分以上表示しても動きが気にならないか
- ネットワークなしで固定状態を再現できるか
- 天気APIが失敗しても画面が崩れないか
- reduced motionでトランジションが抑制されるか
- URLを共有した相手が同じ状態を再現できるか

## 推奨する最終方針

「天気が変わる背景」を前面に出すのではなく、「発表内容を邪魔しない環境の生成器」として完成させます。表現の強さは、アニメーションではなく、低彩度の色・余白・状態の一貫性で出すのが最も相性がよいです。
